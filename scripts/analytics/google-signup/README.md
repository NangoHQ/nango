# Google signup conversion proposal

October 22, 2026. Refs [NAN-7534](https://linear.app/nango/issue/NAN-7534) and [NAN-7683](https://linear.app/nango/issue/NAN-7683). Default off. No credentials, Google action, destination, deployment or live conversions have been provisioned by this change.

The website writes a separate Google cookie only for a permitted Cookiebot marketing choice, no GPC, and a real URL `gclid`, `wbraid` or `gbraid`. It keeps one landing identifier and its original observation time for at most 24 hours. GCLID wins when the same landing has multiple identifier kinds; otherwise WBRAID, then GBRAID. New landings replace the prior Google click. This is a browser observation time, not a verified Google click timestamp. Malformed/absent IDs never fall back to email, IP, UTMs or profile attribution.

The server reads the current cookie at the existing email signup or Google authentication completion. Optional `advertising_google_*` properties attach only to `auth:account_create`. The event means a committed new account before email verification. Invites and returning logins do not create this event. Internal email accounts and request GPC omit advertising context. The destination additionally requires the company group's `is_internal` to be explicitly false and rejects known QA markers. The original strict Meta/OpenAI parser and cookie format are unchanged.

[Cookiebot maps ad_user_data and ad_personalization to marketing](https://support.cookiebot.com/hc/en-us/articles/12756353963292-About-Google-Consent-Mode). The Google fields use that mapping only after the existing explicit-choice or resolved non-opt-in regional-default check. These are browser-reported choices, not independently authenticated CMP evidence. Consent is checked at signup. Later withdrawal may not stop queued delivery or retries, the accepted V1 limitation.

## Proposed delivery

`config.mjs` returns an unsaved configuration. `destination.hog` runs in the existing PostHog destination runtime, with one conversion per request. It accepts only the server account event, matching company identity, permitted Google fields, fresh click/choice and an explicit launch cutoff. It sends the original event timestamp and `nango:account_create:<company>` transaction ID. No extra service, cron, database, webapp state or Google tag is introduced.

[Data Manager supports click identifiers without userData](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events). Fixed endpoints:

- OAuth refresh: `POST https://oauth2.googleapis.com/token`
- Ingestion: `POST https://datamanager.googleapis.com/v1/events:ingest`
- Diagnostics: `GET https://datamanager.googleapis.com/v1/requestStatus:retrieve?requestId=...`

Each eligible invocation refreshes an access token using approved OAuth client ID, secret and refresh token stored as encrypted secret inputs. There is no persisted access token and no interactive authentication during delivery. Missing credentials, revoked refresh grants, bad scope and HTTP failures stop delivery; they cannot block signup because delivery happens in PostHog afterward. The source logs only stage/status, allowlisted reason codes and the opaque request ID. It never prints payloads or raw response bodies. Raw non-JSON responses are refused. Do not use the native mock debugger with real credentials: debugger request dumps can expose dynamically minted tokens. Production runtime redaction remains an approval gate.

The Data Manager scope is `https://www.googleapis.com/auth/datamanager`. A Google Ads connection with only an Ads API scope does not prove access. Native PostHog Google Ads is experimental and uses legacy uploadClickConversions, so this proposal does not install it. Only Slack was connected in the read-only project audit.

## Minimal setup for approval

1. Select a Nango-owned Google Cloud project, approve enabling Data Manager API, and select an approved OAuth client/user. The user must have access to Ads account `5335545931` or its manager. Obtain offline refresh permission for the Data Manager scope through the approved secret provisioning process. Confirm OAuth app audience/publishing status supports durable use and arrange reauthorization on revocation. Do not create a service or service-account key just for this proposal. See [Google access setup](https://developers.google.com/data-manager/api/devguides/quickstart/set-up-access).
2. Create a dedicated action, proposed name `Nango | Account signup | Server`, category `SIGNUP`, type `UPLOAD_CLICKS` / Website (Import from clicks), **Secondary**, counting `MANY` / Every, proposed 30-day click window, no monetary value. Keep it out of account-default and all custom bidding goals. Read back action/goal membership before proceeding. Preserve the demo and historical GA4 actions, campaign bidding and budgets.
3. `MANY` is required for braid support: Google reports `ONE_PER_CLICK_CONVERSION_ACTION_NOT_PERMITTED_WITH_BRAID`. Every permits multiple distinct account conversions per click. The intended unit is one new account, not one per click. GBRAID is documented for iOS app-origin traffic and WBRAID for web; genuine braid matching and this account's eligibility remain unverified. See [identifier definitions](https://developers.google.com/data-manager/api/reference/rest/v1/events/ingest) and [processing errors](https://developers.google.com/data-manager/api/reference/rest/v1/requestStatus/retrieve). No custom variables/cart data are sent.
4. Deploy the server with `SIGNUP_GOOGLE_CONTEXT_ENABLED=false`; configure an explicit Google cookie name distinct from Meta/OpenAI and from Dev. After approval, enable capture server-side, then deploy the website with `PUBLIC_SIGNUP_GOOGLE_CONTEXT_ENABLED=true` and the matching `PUBLIC_SIGNUP_GOOGLE_CONTEXT_COOKIE_NAME`. Suggested names: `nango_signup_google_dev`, `nango_signup_google_prod`. Either rollout order is compatible because old servers ignore the separate cookie, but server first avoids losing Google context. Keep ad delivery disabled.
5. Prepare a separate PostHog destination from `configuration()`: `enabled=false`, `deliveryApproved=false`, `validateOnly=true`; filter `auth:account_create`, test-account exclusions on. Enter customer/login/action IDs, approved encrypted OAuth inputs and a fresh Google-specific UTC launch cutoff. Never reuse the Meta/ChatGPT cutoff or backfill. Keep existing destinations untouched.
6. Obtain approval for credentialed validation separately. Confirm two HTTP continuations, refresh lifecycle, response parsing, secret redaction and retry behavior with `validateOnly=true`. This does not record a conversion and does not prove attribution or asynchronous diagnostics. Do not accept customer-data terms or enable enhanced conversions as a discovery step; escalate any actual required terms or entitlement error.
7. After runtime approval, separately approve `deliveryApproved=true`, `validateOnly=false` and enabling the new destination. Verify the first real eligible signup with its request diagnostics and Ads action receipt. Do not send synthetic live conversions. No positive receipt has been established.

## Receipts, retries and deduplication

[Google fast-fails the whole request](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events). One event/request avoids losing unrelated signups. A successful ingest response only means accepted, not processed or attributed. Check field warning reason codes. Record its opaque request ID and run `configuration(true)` as an unsaved manual diagnostics read with that ID. It never ingests/resends. `PROCESSING` needs another read later. `FAILED` and `PARTIAL_SUCCESS` report allowlisted error reasons; duplicate-transaction-only errors are identified separately. Validation-only requests have no processing diagnostics. Someone must own pending receipts before launch; no automatic polling job is added.

Google documents transaction deduplication within a conversion action and a duplicate order-ID/action processing error. This sender reuses exactly the same account/action transaction ID and original timestamp on transport retries. It does not replace either with ingestion time, a click ID, PostHog UUID or retry counter. No local delivery ledger is added. Google's published references do not specify a dedup retention duration or an exactly-once guarantee. The 90-day click TTL/configured action window concerns click eligibility, not a dedup retention promise. Live retry/dedup behavior remains unverified. If a stronger durable guarantee is required, resolve that with Om before enabling rather than assuming this is exactly once.

[PostHog documents up to three HTTP retries depending on response codes](https://posthog.com/docs/data-pipelines/destinations#how-do-you-handle-retries), and says the policy can change. Both token and ingestion fetches are subject to that runtime. Our code surfaces final non-2xx results without raw bodies. It does not promise which errors or network timeouts are replayed, whether a continuation refreshes an expired bearer token, or that a failed whole invocation automatically restarts. These require a runtime check. Disabling a destination cannot recall already sent data or guarantee queued retries stop.

## Validation and rollback

Synthetic tests execute the actual Hog handler in the connected compiler/runtime with only `fetch` replaced by deterministic responses. `mock-tests.mjs` generates unsaved invocation requests and verifies payload allowlists, Google consent, all three identifiers, duplicates, cutoff/QA/internal exclusions, token failures, response redaction, validate-only and processing diagnostics. All values are fake. This checks handler behavior, not real HTTP continuation or platform attribution. Native `mock_async_functions=true` returns a generic placeholder body without an OAuth token. The unmodified sources compile and correctly reject that placeholder; this cannot establish real OAuth/retry behavior.

Keep helpers' returns outside `try` blocks. In this runtime, returning inside `try` swallowed later handler errors during the deterministic tests. Do not parse raw response text: parser VM exceptions did not pass through a normal catch.

Rollback: disable only the new Google destination, then turn off Google capture flags and clear the Google cookie with the same domain/path attributes if needed. Preserve the original signup event and Meta/ChatGPT setup. An old server ignores this cookie; an old website emits no Google cookie. Invalid Google input leaves the existing Meta/ChatGPT context and signup intact.
