# Google signup conversion setup

Default-off proposal for [NAN-7534](https://linear.app/nango/issue/NAN-7534) / [NAN-7683](https://linear.app/nango/issue/NAN-7683). Companion: [website #168](https://github.com/NangoHQ/website/pull/168). No credentials, conversion action, destination or deployment has been provisioned.

## Behavior

A separate Google cookie retains one genuine landing `gclid`, `wbraid` or `gbraid`, its original browser observation time and the current permitted Cookiebot choice. GCLID takes precedence on a landing containing multiple kinds, then WBRAID, then GBRAID. A newer Google landing replaces the prior identifier. The **24-hour click/choice lifetime is our deliberate V1 limit**, separate from the proposed **30-day Google action window**. No email, IP, UTM or profile fallback.

[Cookiebot maps Google's ad_user_data and ad_personalization to marketing](https://support.cookiebot.com/hc/en-us/articles/12756353963292-About-Google-Consent-Mode). Existing explicit-choice/resolved regional-default and GPC checks apply. Denial/withdrawal clears the cookie. The server adds optional Google fields only to committed `auth:account_create`, before email verification. Invites, returning login and internal signups retain existing behavior. The released Meta/ChatGPT cookie format and strict parser are unchanged.

`destination.hog` reuses PostHog's destination runtime. Each eligible server account event sends one click-only request, original signup timestamp and `nango:account_create:<company>` transaction ID. It requires a matching account, explicitly external company, fresh choice/click, launch cutoff and delivery approval. No new service, job or database. Consent remains browser-reported and checked at signup; later withdrawal may not stop queued sends/retries, the accepted V1 limitation.

## Approval and setup

1. **Cloud/OAuth:** Select an approved Nango Cloud project and approve Data Manager API enablement. Use an approved OAuth user/client with offline scope `https://www.googleapis.com/auth/datamanager` and Ads account `5335545931` access, directly or through its manager. Confirm durable refresh/app publishing status and a reauthorization owner. Put client ID, secret and refresh token only in encrypted PostHog secret inputs. No service-account key is needed. [Google prerequisites](https://developers.google.com/data-manager/api/devguides/quickstart/set-up-access).
2. **Dedicated action:** Proposed `Nango | Account signup | Server`, type `UPLOAD_CLICKS` / Website (Import from clicks), category `SIGNUP`, **Secondary**, **MANY/Every**, proposed 30-day click window, no monetary value. Read back exclusion from account-default and every custom bidding goal. Preserve campaign bidding, budgets, demo and historical GA4 actions. Google rejects braid conversions on One-per-click actions. Every permits separate account conversions from one click; our intended unit is one new account. [Identifier and action requirements](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events), [braid constraints](https://developers.google.com/data-manager/api/reference/rest/v1/requestStatus/retrieve).
3. **Capture rollout:** After review and deployment approval, deploy server first, then website. Both Google flags default off: `SIGNUP_GOOGLE_CONTEXT_ENABLED` and `PUBLIC_SIGNUP_GOOGLE_CONTEXT_ENABLED`. Configure matching explicit `*_COOKIE_NAME` values, different from Meta/ChatGPT and between Dev/Prod, e.g. `nango_signup_google_dev` / `nango_signup_google_prod`. Separate cookies make either rollout order compatible; server first avoids losing context. Keep delivery off.
4. **Destination:** `configuration()` in `config.mjs` produces an unsaved, disabled definition. Supply customer/login/action IDs, approved OAuth inputs and a **fresh Google-specific UTC cutoff**. Keep `deliveryApproved=false`, `validateOnly=true`, event filter and test-account exclusions. No backfill; leave existing destinations untouched. Native PostHog Google Ads is experimental/legacy and is not installed by this proposal.
5. **Runtime gate:** Separately approve credentialed `validateOnly=true` checks: OAuth refresh lifecycle, both HTTP continuations, secret redaction and retry behavior. Never use native debugger request dumps with real credentials; dynamically minted tokens may be exposed there. Do not accept terms or enable enhanced conversions as discovery. Escalate any actual entitlement/terms error.
6. **Launch gate:** After runtime validation, separately approve production capture/deploy and destination enablement with `deliveryApproved=true`, `validateOnly=false`. Assign an owner for pending request diagnostics. Verify the first real eligible signup's processing diagnostics and Ads receipt. No synthetic live conversions.

## Delivery and diagnostics

Fixed endpoints: `oauth2.googleapis.com/token` (POST refresh per eligible invocation), `datamanager.googleapis.com/v1/events:ingest` (POST) and `datamanager.googleapis.com/v1/requestStatus:retrieve?requestId=...` (GET). Refresh failures occur after signup in PostHog and cannot block signup. Source logging is limited to stage/status, allowlisted reason codes and opaque request IDs; no raw payloads/responses. Production runtime redaction remains unverified.

Ingestion acceptance is not processing or attribution. [Google fast-fails a whole request](https://developers.google.com/data-manager/api/devguides/events/google-ads/offline/send-events); one event/request isolates failures. Check warning codes, retain `requestId`, then run `configuration(true)` as an unsaved manual diagnostics read. It never resends. `PROCESSING` needs another read later; `FAILED`/`PARTIAL_SUCCESS` report error reasons. Duplicate-transaction-only errors are distinguished. Validation-only requests have no processing diagnostics.

Google documents transaction-ID deduplication within a conversion action, but **no dedup retention duration or exactly-once guarantee was established**. Retries retain the account/action ID and original timestamp. The click TTL/action window is not a dedup retention promise. No local delivery ledger is added; stronger guarantees require a decision before launch. Genuine braid matching, account eligibility and live dedup remain unverified.

[PostHog documents up to three HTTP retries depending on response codes](https://posthog.com/docs/data-pipelines/destinations#how-do-you-handle-retries), subject to change. Both token and ingestion calls use that runtime. Which failures replay, whether an expired token is refreshed on a delayed continuation, and whether a whole invocation restarts remain unverified.

## Evidence and rollback

13 website tests, 178 backend unit/schema tests, 23 local Docker signup tests and 40 deterministic Hog cases pass; builds/typecheck/format and targeted lint pass with existing warnings. Deterministic tests execute the actual handler with fake response transport, not real OAuth or retry scheduling. Native mocks verify compilation and missing-token handling. First real receipt remains pending. `mock-tests.mjs` documents generation/verification commands. Keep helper returns outside `try`; this runtime swallowed later errors when a helper returned inside `try`. Raw-text parser VM errors were not caught, so responses fail closed unless already JSON-decoded.

Rollback: disable only the Google destination, turn off Google capture flags and clear its cookie using the same domain/path. Old servers ignore the separate cookie. Signup and Meta/ChatGPT continue. Disabling cannot recall sent data or guarantee queued retries stop.
