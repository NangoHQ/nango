Trigger authorization flows in your frontend with this SDK. It is available on [NPM](https://www.npmjs.com/package/@nangohq/frontend) as `@nangohq/frontend`.

## Instantiate the frontend SDK

```ts
import Nango from '@nangohq/frontend';

const nango = new Nango({ connectSessionToken: '<CONNECTION-SESSION-TOKEN>' });
```

**Parameters**

<Expandable>
  <ResponseField name="config" type="object" required>
    <Expandable title="options" defaultOpen>
      <ResponseField name="connectSessionToken" type="string">
        A connect session token created by your backend with the [create connect session API](/reference/backend/http-api/connect/sessions/create), or the [reconnect session API](/reference/backend/http-api/connect/sessions/reconnect) to re-authorize an existing connection. Used by `nango.auth`, `nango.create` and `nango.reconnect`, and required by `nango.reconnect`.
      </ResponseField>

      <ResponseField name="publicKey" type="string" deprecated>
    Get your public key in the environment settings of the Nango UI. This key is not sensitive. Use `connectSessionToken` instead.
      </ResponseField>

      <ResponseField name="host" type="string">
        Omitting the host points to Nango Cloud. For local development, use `http://localhost:3003`. Use your instance URL if self-hosting.
      </ResponseField>

      <ResponseField name="websocketsPath" type="string">
        For self-hosted instances only to specify a customs path for the WebSocket connection.
      </ResponseField>

      <ResponseField name="width" type="number">
        Specify a specific width for the OAuth authorization modal.
      </ResponseField>

      <ResponseField name="height" type="number">
        Specify a specific height for the OAuth authorization modal.
      </ResponseField>

      <ResponseField name="debug" type="boolean">
        Print additional console logs to debug authorization issues.
      </ResponseField>
    </Expandable>
  </ResponseField>
</Expandable>


## Connect using Nango Connect UI

Nango provides a UI component that guides your app's users through automatically and securely setting up an integration. This UI is hosted on Nango's servers and requires minimal setup on your end to get started quickly.
This is the recommended way to use Nango in your frontend.

```js
const connectUI = nango.openConnectUI({ sessionToken: 'SESSION_TOKEN' });
```

**Parameters**
<Expandable>
  <ResponseField name="sessionToken" type="string">
    The unique token to identify your user. It is required but can be set asynchronously with `connectUI.setSessionToken()`. Defaults to the `connectSessionToken` passed to the `Nango` constructor.
  </ResponseField>

  <ResponseField name="baseURL" type="string" default="https://connect.nango.dev">
    The base URL to load the UI
  </ResponseField>

  <ResponseField name="apiURL" type="string" default="https://api.nango.dev">
    The base URL to reach Nango API
  </ResponseField>

  <ResponseField name="onEvent" type="function">
    A callback to listen to events sent by Nango Connect. Each event has a `type`: `ready`, `connect` (with `payload.providerConfigKey` and `payload.connectionId`), `error` (with `payload.errorType` and `payload.errorMessage`), `close` or `settings_changed`.
  </ResponseField>

  <ResponseField name="detectClosedAuthWindow" type="boolean" default="false">
    Control OAuth popup close detection. If set to true, a closed popup will be detected as a failed authorization.
  </ResponseField>

  <ResponseField name="lang" type="string">
    The language to use for the UI. Defaults to browser language or english if not supported.
  </ResponseField>

  <ResponseField name="themeOverride" type="string">
    The theme (light, dark, system) to use for the UI. Overrides your global setting in the dashboard.
  </ResponseField>
</Expandable>

**Response**

<Expandable>
  <ResponseField name="connectUI" type="ConnectUI">
    The class to manipulate Nango Connect, with these methods:
    - `setSessionToken(sessionToken)`: set the session token after opening the UI. A loading indicator shows until it's set.
    - `close()`: close the UI.
  </ResponseField>
</Expandable>

## Connect using the headless client

You store end-user credentials with the `nango.auth` method. It creates a connection in Nango.

For OAuth and the other popup-based modes (GitHub App, GitHub App OAuth, MCP OAuth and plugin installs), `nango.auth` opens a popup. For credential-based modes, pass the credentials you collected and the connection is created directly, with no popup. Field names for the two-step and JWT modes are the `credentials` fields of the integration's provider in [providers.yaml](https://github.com/NangoHQ/nango/blob/master/packages/providers/providers.yaml).

<Warning>
The frontend SDK runs in your user's browser, so only pass credentials your end user entered. Never hard-code your own app's secrets, such as client secrets, private keys or developer keys, in frontend code. To create a connection with credentials you hold on your server, use the [import connection API](/reference/backend/http-api/connections/post) from your backend.
</Warning>


<Tabs>

<Tab title="OAuth">

For OAuth (OAuth 2, OAuth 1, GitHub App, GitHub App OAuth, MCP OAuth and plugin installs such as Crisp), this will open a modal to let the user log in to their external account.

```js
const result = await nango.auth('<INTEGRATION-ID>').catch((error) => {
...
});
```

</Tab>

<Tab title="API Key">

For API key authorization, pass the end-user's previously-collected API key directly in the parameters.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { apiKey: '<END-USER-API-KEY>' }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="Basic Auth">

For Basic Auth, pass the end-user's previously-collected username & password in the parameters.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { username: '<END-USER-USERNAME>', password: '<END-USER-PASSWORD>' }
}).catch((error) => {
    ...
});
```
</Tab>

<Tab title="OAuth 2 client credentials">

For OAuth 2 client credentials, pass the end-user's client ID and client secret. Nango fetches the access token, and a new one when it expires.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { client_id: '<CLIENT-ID>', client_secret: '<CLIENT-SECRET>' }
}).catch((error) => {
    ...
});
```

For integrations that authenticate the client with a certificate (mTLS) or a private key, pass `client_certificate` and `client_private_key` (PEM) instead of, or in addition to, `client_secret`, as the integration requires.

</Tab>

<Tab title="Two-step">

For two-step auth (Nango exchanges the credentials for a token, e.g. Google Service Account), set `type: 'TWO_STEP'` and pass the integration's credential fields.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: {
        type: 'TWO_STEP',
        serviceAccountEmailAddress: 'svc@project.iam.gserviceaccount.com',
        privateKey: '-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n',
        scopes: 'https://www.googleapis.com/auth/gmail.readonly',
        delegatedAccessEmailAddress: 'user@example.com'
    }
}).catch((error) => {
    ...
});
```

Nango requests a token while creating the connection, so invalid credentials fail the call.

</Tab>

<Tab title="JWT">

For JWT auth (Nango signs a JWT with the credentials, e.g. Ghost Admin), set `type: 'JWT'` and pass the integration's credential fields. For Ghost Admin, `privateKey` is the Admin API key in `<id>:<secret>` format.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { type: 'JWT', privateKey: '<KEY-ID>:<KEY-SECRET>' },
    params: { adminDomain: '<END-USER-ADMIN-DOMAIN>', version: 'v5.0' }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="Signature">

For signature-based auth (Nango signs each request with the credentials, e.g. Emarsys), set `type: 'SIGNATURE'` and pass the username and secret.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { type: 'SIGNATURE', username: '<END-USER-USERNAME>', password: '<END-USER-SECRET>' }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="TBA">

For token-based authentication (NetSuite TBA), pass the token ID and token secret. Add `oauth_client_id_override` and `oauth_client_secret_override` when your users bring their own integration record.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: {
        token_id: '<END-USER-TOKEN-ID>',
        token_secret: '<END-USER-TOKEN-SECRET>',
        oauth_client_id_override: '<END-USER-CONSUMER-KEY>',
        oauth_client_secret_override: '<END-USER-CONSUMER-SECRET>'
    },
    params: { accountId: '<END-USER-ACCOUNT-ID>' }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="Bill">

For Bill, pass the username, password, organization ID and developer key.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: {
        username: '<END-USER-USERNAME>',
        password: '<END-USER-PASSWORD>',
        organization_id: '<END-USER-ORGANIZATION-ID>',
        dev_key: '<DEVELOPER-KEY>'
    }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="AWS SigV4">

For AWS Signature Version 4, set `type: 'AWS_SIGV4'` and pass the ARN of the IAM role Nango assumes. Nango assumes the role while creating the connection and always sends an external ID. If the role's trust policy requires one, generate a UUID, have your user add it to the trust policy, and pass it as `params.external_id`. Otherwise Nango generates a random UUID, which a trust policy that requires an external ID won't match. `region` is optional when the integration has a default region. On reconnect, the stored external ID and region are kept.

```js
const result = await nango.auth('<INTEGRATION-ID>', {
    credentials: { type: 'AWS_SIGV4', role_arn: 'arn:aws:iam::123456789012:role/<ROLE-NAME>', region: 'us-east-1' },
    params: { external_id: '<UUID-IN-THE-TRUST-POLICY>' }
}).catch((error) => {
    ...
});
```

</Tab>

<Tab title="No auth">

For integrations that need no credentials, use `nango.create` instead of `nango.auth`.

```js
const result = await nango.create('<INTEGRATION-ID>').catch((error) => {
    ...
});
```

</Tab>

</Tabs>

          </ResponseField>

## Reconnect an existing connection

To re-authorize an existing connection, for example after its credentials expired or were revoked, create a reconnect session token with the [reconnect session API](/reference/backend/http-api/connect/sessions/reconnect) and call `nango.reconnect`. It takes the integration ID and the same options as `nango.auth`, and keeps the connection ID.

```js
const nango = new Nango({ connectSessionToken: '<RECONNECT-SESSION-TOKEN>' });

const result = await nango.reconnect('<INTEGRATION-ID>').catch((error) => {
    ...
});
```

`nango.reconnect` throws `missing_connect_session_token` if the SDK was instantiated without a connect session token.

## Error Handling

The Nango Frontend SDK may throw different types of errors during authentication and connection setup. Below are the error types the SDK defines. For headless flows, `type` can also be any error code returned by the Nango API (e.g. `unknown_provider_config`).

1. `missing_auth_token`
   - Occurs when neither a public key nor a connect session token is provided.
   - Message: "You must specify a public key OR a connect session token (cf. documentation)."

2. `blocked_by_browser`
   - Occurs when the browser blocks the popup window for authentication.
   - Message: "Modal blocked by browser"

3. `invalid_host_url`
   - Occurs when the provided host URL is invalid.
   - Message: "Invalid URL provided for the Nango host."

4. `missing_credentials`
   - Occurs when required credentials are not provided, including `installation: 'outbound'` without a `credentials` object.
   - Message: "You must specify credentials." or "Credentials are required for custom auth"

5. `window_closed`
   - Occurs when the authentication window is closed before completing the flow.
   - Message: "The authorization window was closed before the authorization flow was completed"

6. `connection_test_failed`
   - Occurs when credential verification fails for certain integrations before the connection is established.
   - Message: "The given credentials were found to be invalid. Please check the credentials and try again."

7. `connection_validation_failed`
   - Occurs when your [connection validation function](/guides/functions/event-functions#create-a-connection-validation-function) rejects the connection.
   - Message: The message returned by your validation function.

8. `missing_connect_session_token`
    - Occurs when attempting to reconnect without a session token.
    - Message: "Reconnect requires a session token"

9. `resource_capped`
    - Occurs when the resource usage limit has been reached.
    - Message: "Reached maximum number of allowed connections. Upgrade your plan to get rid of connection limits."

10. `unknown_error`
    - Occurs when an unexpected error happens that doesn't fall into other error categories.
    - Message: Varies depending on the underlying error (e.g., network failures, unexpected exceptions)

### Error Response Structure

Errors returned by the Nango API follow this structure. The SDK turns `code` into the `AuthError`'s `type`, and `message` into its `message`:

```json
{
    "error": {
        "code": "<error_type>",
        "message": "<detailed_error_message>"
    }
}
```

### Handling Errors

You can handle these errors in your code using the `AuthError` class.

```ts
import { AuthError } from '@nangohq/frontend';

try {
    const result = await nango.auth('<INTEGRATION-ID>', {
        credentials: { apiKey: '<END-USER-API-KEY>' }
    });
} catch (error) {
    if (error instanceof AuthError && error.type === '<error_type>') {
        // Handle specific error
        console.error('Your error message');
    }
}
```
