Bring Your Own Cloud (BYOC) gives you a dedicated Nango instance running inside your own AWS, GCP, or Azure account, in the region of your choice. Nango installs it, then operates, monitors, updates, and scales it for you.

Everything Nango handles — API credentials, synced records, logs, and the audit trail — is stored and processed inside your account. Nango is not a subprocessor for your customers' data.

## Choosing a deployment model

We recommend **Nango Cloud** for most teams: No operational overhead, [SOC 2 Type II, GDPR and HIPAA compliant](/guides/platform/security#compliance), auto-scales to virtually any load, and is used in production by Fortune 500 companies.

Choose **BYOC** when a specific requirement makes it necessary:

| Requirement | Why BYOC |
| - | - |
| **Data residency** | Customer data must be stored and processed in a particular country or region |
| **Compliance regimes** | FedRAMP and similar advanced compliance programs |

Self-hosting, fully managed by you, is also available.

Please reach out, we are happy to help you evaluate which deployment fits best for your use case!

<Info>
Nango is open source and can be [self-hosted for free](/guides/platform/free-self-hosting) for hobby projects, with a limited feature set and no managed operations or support.
</Info>

## How BYOC works

Nango deploys a complete, dedicated Nango stack into your cloud account using Terraform and GitOps, then manages it from there. The instance is yours alone — no infrastructure is shared with other Nango customers.

You can run it in any region of AWS, GCP, or Azure. BYOC instances have all features of the [Enterprise plan](https://nango.dev/pricing).

| Component | Role |
| - | - |
| Server | Dashboard, API, proxy requests, and incoming and outgoing webhooks |
| Orchestrator | Task scheduling and state tracking |
| Jobs | Processes tasks and dispatches them to the Runner |
| Runner | Executes your integration code and calls external APIs |
| Persist | Writes synced records and logs |
| PostgreSQL | Control plane, API credentials, scheduled tasks, and synced records |
| Object storage | Compiled integration code |
| Elastic/Opensearch | Execution logs |
| Redis | Socket state, token refresh locks, and rate limits |

Nango maps each of these onto your cloud provider's managed services, and provisions the surrounding network, load balancing, secret storage, and TLS certificates as part of the deployment.

## What Nango needs from you

A cloud account, and scoped access to it.

You create a role or service account that Nango's deployment identity can assume:

- **Reviewable** — you get the exact permission definition as an infrastructure-as-code template before you apply it.
- **No long-lived keys** — access uses short-lived tokens, issued only while the grant stands.
- **Scoped** — it covers what the deployment needs. We can narrow it further with a dedicated account, custom roles, or network restrictions.
- **Revocable** — remove the grant and access ends immediately. Your instance keeps running, but Nango can no longer manage it.

The first deployment typically completes in under a week.

## Security and shared responsibility

### Who is responsible for what

**Nango** is responsible for the Nango software and the components it deploys: installing the instance, then maintaining, updating, monitoring, and scaling it.

**You** are responsible for the cloud account it runs in: account-level access, the network perimeter and its configuration, your own IAM, and the cost of the cloud resources.

We are happy to work with you on the boundary between those.

### What leaves your account

Only anonymized telemetry — object identifiers carrying no customer data — is sent to Nango's observability platform (Datadog), which can be hosted in the US, EU, or APAC.

We use this telemetry data solely to operate, maintain and scale your instance.

### Credentials and encryption

Nango's software performs token exchange, token refresh, and encryption. The encryption key lives in your account's key management service, and every encrypted value is written to your database. The identity Nango uses to deploy and manage the instance holds no permission to decrypt — only the running workloads do.

Encryption algorithms, retention windows, and deletion behavior match Nango Cloud, documented on the [Security](/guides/platform/security) page. On BYOC, retention values are configurable, and we set them with you during onboarding.

### Compliance

Nango is [SOC 2 Type II certified, GDPR compliant, and HIPAA compliant](/guides/platform/security#compliance).

Because the instance runs in your account, and Nango cannot access your customer's data, **Nango is not a subprocessor for your customers' data**.

## Operating your instance

Nango operates the instance: updates, monitoring, scaling, and incident response. Announcements about your instance go to your dedicated Slack channel, and Nango gives you advance notice before introducing new infrastructure, such as an additional database.

### Scaling

Instances auto-scale with load, and Nango manages the scaling policies in collaboration with your team.

### What you can see

- [Observability](/guides/platform/observability) in the dashboard, covering auth flows, function executions, and proxy requests.
- The [audit trail](/guides/platform/audit-trail), recording control-plane changes with actor, outcome, and originating IP.
- [OpenTelemetry export](/guides/platform/observability#opentelemetry-export) into your own monitoring tooling.

### SLA and support

BYOC instances include:

- Uptime SLA with service credits
- Premium support on Slack Connect
- Access to a Nango solutions engineer to architect & scale your integrations

### Costs

You pay your cloud provider directly for compute, storage, and network. Nango's fee covers the software license and Nango's operation of the instance.
