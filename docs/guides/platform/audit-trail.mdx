# Audit trail

The audit trail records **control-plane** activity in your Nango account — the operations that configure it and manage who can reach it: who deleted a connection, who changed an integration's settings, who changed a teammate's role, who signed in. Each entry captures the actor, the action, the affected resource, and the outcome, so you can answer "who did this, and when" during an incident or a compliance review.

Entries are immutable. Nango never edits or deletes an entry before its retention period ends.

## Availability

Recording and access are separate, and are enabled per account — contact us to have either turned on.

| | |
|---|---|
| **Recording** | Available on paid plans |
| **Viewing and export** | Enterprise |
| **Retention** | 1 year |

Because they are separate, Nango can be recording your account's activity before the dashboard is available to you, so nothing is lost while access is being set up.

Retention is stamped on each entry when it is written and never recalculated, so a change to your plan or to the retention period does not re-time entries already recorded.

## Reading the audit trail

The audit trail lives in the Nango dashboard under **Audit trail**, in the menu behind your profile. It is account-wide rather than per-environment, so it covers activity across every environment in one place.

Every entry carries:

| Field | Description |
|-------|-------------|
| `occurredAt` | When the action happened |
| `actor` | Who performed it — see [Actors](#actors) |
| `resource` and `action` | What was done, for example `connection` + `deleted` |
| `targets` | What it was done to, such as a connection ID or a teammate's email |
| `outcome` | `success`, `failure`, or `denied` — a rejected attempt is recorded, not dropped |
| `environment` | The environment involved, or empty for account-level actions |
| `context` | The originating IP address and user agent, and which interface was used (`api` or `mcp`) |

Denied attempts matter as much as successful ones: an entry with outcome `denied` tells you someone tried an action they were not permitted to perform.

<a id="what-is-recorded"></a>
## What is recorded

The audit trail covers the main control-plane operations: connections, integrations, functions, syncs, API keys, environments, team membership, authentication, and billing. Each entry pairs a `resource` with an `action`:

- `connection` — `created`, `updated`, `metadata_updated`, `refreshed`, `deleted`
- `integration` — `created`, `updated`, `deleted`
- `function` — `deployed`, `upgraded`, `deleted`
- `sync` — `enabled`, `disabled`, `paused`, `started`, `triggered`, `cancelled`, `frequency_changed`, `variant_created`, `variant_deleted`
- `api_key` — `created`, `updated`, `deleted`
- `environment` — `created`, `updated`, `variables_changed`, `webhook_urls_changed`, `webhook_signing_key_rotated`, `deleted`
- `member` — `invited`, `invite_accepted`, `invite_declined`, `invite_revoked`, `removed`, `role_changed`
- `team` — `updated`
- `user` — `updated`
- `app_auth` — `login`, `logout`, `signup`, `password_changed`, `password_reset`
- `mfa` — `enrolled`, `enabled`, `disabled`, `verified`, `recovery_regenerated`
- `billing` — `plan_changed`, `trial_extended`, `details_changed`, `payment_method_added`, `payment_method_removed`

These are recorded wherever the operation is performed — the Nango dashboard, the public API, the CLI, and the management MCP server all produce entries, and `context.interface` tells you which. Connections are recorded however they are created: through the Connect UI, an OAuth flow, one of the per-auth-mode endpoints, or an import.

Secrets never appear in an entry: API key values, passwords, TOTP and recovery codes, card details, and environment variable values. Variable *names* are recorded.

<a id="actors"></a>
## Actors

| Actor | Meaning |
|-------|---------|
| `user` | Someone signed in to the Nango dashboard |
| `api_key` | A call authenticated with an API key. The entry names the key, so you can tell which one |
| `connect_session` | The end user who completed a Connect flow, identified by the end-user ID you supplied when creating the session, and their email if you supplied one |
| `anonymous` | A genuinely unauthenticated attempt — a rejected sign-in, for example |
| `unknown` | A caller Nango could not attribute. See below |

Three cases are worth knowing about, because they limit what an entry can tell you:

- **Connections created through the deprecated public-key frontend flow are recorded as `unknown`.** That flow identifies an environment rather than a person, and carries no end user, so there is nobody to name. Moving to [connect sessions](/guides/auth/auth-guide) fixes it.
- **Calls your functions make to the Nango API appear as `api_key`**, naming the environment's key rather than the function, because they authenticate the same way a person with that key would.
- **A rejected sign-in is recorded as `anonymous`**, with the attempted email as the target rather than the actor — the attempt did not prove who it came from.

<a id="what-is-not-recorded"></a>
## What is not recorded

The audit trail covers the control plane, not the **data plane** — the day-to-day API traffic your integrations generate to move data in and out of external APIs.

<Warning>
**Credential reads are not recorded.** Retrieving a connection's credentials — `GET /connection/{connectionId}` with credentials returned, and the SDK helpers built on it such as `getConnection()`, `getToken()`, and `getRawTokenResponse()` — produces no audit entry. If you need to know when a customer's access token was read, the audit trail will not tell you. Contact us if this matters for your compliance requirements.
</Warning>

**Data access and data movement are not recorded.** None of the following produce entries:

| Not recorded | Examples |
|--------------|----------|
| Reading credentials | `GET /connection/{connectionId}` |
| Reading records | `GET /records` |
| Deleting records | `PATCH /records` pruning |
| Proxy requests | Every call through `/proxy` |
| Action executions | `POST /action/trigger` |
| Sync triggers over the public API | `POST /sync/trigger` |
| Reading configuration | Listing or fetching connections, integrations, or functions |

<Note>
Reads are generally not recorded. Listing connections, fetching an integration, or opening a page in the dashboard leaves no entry. The audit trail answers "what changed", not "what was looked at".
</Note>

If you need coverage of credential reads or data access, get in touch — we want to hear which events matter to you before we build them.

## Self-hosted Nango

The audit trail is not yet available on self-hosted Nango.
