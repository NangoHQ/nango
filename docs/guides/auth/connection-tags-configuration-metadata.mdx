A Nango connection can store several kinds of information besides credentials. Use the right field depending on what the data does.

| Field | Use it for | Example |
| --- | --- | --- |
| `tags` | Link connections to your app's records, find them later, and scope access | `end_user_id`, `organization_id`, `workspace_id` |
| `connection_config` | Provider-specific information required for the connection to be valid or usable | `subdomain`, `tenantId`, `region`, API base URL |
| `metadata` | Your own application or function configuration stored on the connection | field mappings, selected folder IDs, feature flags |

## Connection tags

Connection tags are key-value labels that link a Nango connection to the user, organization, project, workspace, or other entity it belongs to in your app.

Example tags include `end_user_id: user_123`, `organization_id: org_456`, `workspace_id: ws_789`, and `department: finance`.

Choose tags based on how your app needs to [find connections](#filter-connections-by-tags) and control access. For an internal integration, you can tag Finance's shared connections with `department: finance` and [scope an agent session](/guides/agent-sessions/tenant#select-connections-by-tags-recommended) to that department.

Set tags when you create a Connect session. Nango tags the resulting connection and includes those tags in auth webhooks. Save the connection ID in your app if you need to reference a specific connection directly.

<Tip>
  To make connections easier to identify in the Nango dashboard, set `end_user_display_name` and `end_user_email`. Nango uses these reserved UI tags to populate the connections list and connection detail page.
</Tip>

<Note>
  Tags are designed for identifiers and routing metadata. Avoid putting secrets or large/free-form payloads in tags.
</Note>

### Add tags when creating a Connect session

When requesting a new Connect session token from Nango, pass a `tags` object:

<Tabs>
  <Tab title="Node">
    ```ts
    import { Nango } from '@nangohq/node';

    const nango = new Nango({ apiKey: process.env['<NANGO-API-KEY>'] });

    api.post('/sessionToken', async (req, res) => {
      const { data } = await nango.createConnectSession({
        tags: {
          end_user_id: '<END-USER-ID>',
          end_user_email: '<END-USER-EMAIL>',
          organization_id: '<ORGANIZATION-ID>'
        },
        allowed_integrations: ['<INTEGRATION-ID>']
      });

      res.status(200).send({ sessionToken: data.token });
    });
    ```
  </Tab>
  <Tab title="cURL">
    ```bash
    curl --request POST \
      --url https://api.nango.dev/connect/sessions \
      --header 'Authorization: Bearer <NANGO-API-KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "tags": {
          "end_user_id": "<END-USER-ID>",
          "end_user_email": "<END-USER-EMAIL>",
          "organization_id": "<ORGANIZATION-ID>"
        },
        "allowed_integrations": [
          "<INTEGRATION-ID>"
        ]
      }'
    ```
  </Tab>
</Tabs>

### Filter connections by tags

Filter by tags to find the connections for a user, organization, or workspace in your app. A connection must match all the tag keys and values you pass (AND).

<Tabs>
  <Tab title="Node">
    ```ts
    import { Nango } from '@nangohq/node';

    const nango = new Nango({ apiKey: '<NANGO-API-KEY>' });

    const { connections } = await nango.listConnections({
      tags: {
        end_user_id: '<END-USER-ID>',
        organization_id: '<ORGANIZATION-ID>'
      },
      limit: 100
    });

    console.log(connections);
    ```
  </Tab>
  <Tab title="cURL">
    ```bash
    curl --get \
      --url https://api.nango.dev/connections \
      --header 'Authorization: Bearer <NANGO-API-KEY>' \
      --data-urlencode 'tags%5Bend_user_id%5D=<END-USER-ID>' \
      --data-urlencode 'tags%5Borganization_id%5D=<ORGANIZATION-ID>'
    ```
  </Tab>
</Tabs>

### Update tags on an existing connection

If you need to update tags after a connection is created, patch the connection:

<Note>
  Updating tags replaces the whole tag object. If you want to add or remove a single tag, fetch the current connection first, merge locally, then patch.
</Note>

<Tabs>
  <Tab title="Node">
    ```ts
    import { Nango } from '@nangohq/node';

    const nango = new Nango({ apiKey: '<NANGO-API-KEY>' });

    await nango.patchConnection(
      {
        connectionId: '<CONNECTION-ID>',
        provider_config_key: '<INTEGRATION-ID>'
      },
      {
        tags: {
          end_user_id: '<END-USER-ID>',
          end_user_email: '<END-USER-EMAIL>',
          organization_id: '<ORGANIZATION-ID>',
          environment: '<ENVIRONMENT>'
        }
      }
    );
    ```
  </Tab>
  <Tab title="cURL">
    ```bash
    curl --request PATCH \
      --url 'https://api.nango.dev/connections/<CONNECTION-ID>?provider_config_key=<INTEGRATION-ID>' \
      --header 'Authorization: Bearer <NANGO-API-KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "tags": {
          "end_user_id": "<END-USER-ID>",
          "end_user_email": "<END-USER-EMAIL>",
          "organization_id": "<ORGANIZATION-ID>",
          "environment": "<ENVIRONMENT>"
        }
      }'
    ```
  </Tab>
</Tabs>

<a id="reserved-ui-tag-keys"></a>

### Reserved UI tags

Two tags help you identify connections in the Nango dashboard.

- `end_user_display_name` - shown instead of the connection ID in the connections list, making it easier to identify who a connection belongs to
- `end_user_email` - Nango shows it alongside `end_user_display_name` in the connections list. The domain from the email address is also used to display the end user's company logo on the connection detail page.

### Tag rules

- A connection can have up to 10 tags.
- Keys have up to 64 characters. Start with a letter and use only letters, numbers, underscores, hyphens, periods, or slashes.
- Keys are case-insensitive. Nango lowercases them and rejects duplicates after lowercasing.
- Values are case-sensitive strings of 1–255 characters. `end_user_email` must be a valid email address.

## Connection configuration

Connection configuration is provider-specific information stored on a connection because the connection needs it to work.

It can be required to:

- build an OAuth authorization URL, such as a Zendesk subdomain
- choose the correct API base URL, such as a region or account-specific host
- call API endpoints later, such as a tenant ID, account ID, portal ID, or workspace ID
- store values Nango discovers during authorization, such as an API instance URL or provider account ID

Use connection configuration when the value is part of the connection's validity. If the value is missing, the connection may fail to authorize, fail credential checks, or be unusable for API requests.

When you use the pre-built [Connect UI](/guides/auth/overview), Nango generates the required forms for the integration and stores the submitted values as connection configuration.

When you use [headless auth with a custom UI](/guides/auth/customize-connect-ui#build-your-own-auth-ui), you must collect required connection configuration in your own UI and pass it to `nango.auth()`:

```js
nango.auth('zendesk', {
    params: { subdomain: '<ZENDESK-SUBDOMAIN>' }
});
```

You can also set defaults when creating a Connect session:

<Tabs>
  <Tab title="Node">
    ```ts
    const { data } = await nango.createConnectSession({
      allowed_integrations: ['<INTEGRATION-ID>'],
      integrations_config_defaults: {
        '<INTEGRATION-ID>': {
          connection_config: {
            '<CONFIG-KEY>': '<VALUE>'
          }
        }
      }
    });
    ```
  </Tab>
  <Tab title="cURL">
    ```bash
    curl --request POST \
      --url https://api.nango.dev/connect/sessions \
      --header 'Authorization: Bearer <NANGO-API-KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "allowed_integrations": ["<INTEGRATION-ID>"],
        "integrations_config_defaults": {
          "<INTEGRATION-ID>": {
            "connection_config": {
              "<CONFIG-KEY>": "<VALUE>"
            }
          }
        }
      }'
    ```
  </Tab>
</Tabs>

Read connection configuration from the connection:

```ts
const connection = await nango.getConnection('<INTEGRATION-ID>', '<CONNECTION-ID>');

console.log(connection.connection_config);
```

For the REST API response shape, see [Get a connection](/reference/backend/http-api/connections/get). For the Node SDK method, see [Get a connection with credentials](/reference/backend/backend-sdk/node#get-a-connection-with-credentials).

## Connection metadata

Connection metadata stores settings for your app and Nango functions as a JSON object on each connection.

Good metadata examples:

- field mappings chosen by a customer
- folder, project, board, or object IDs selected during onboarding
- filters and feature flags used by Nango functions and tools
- tenant-specific identifiers discovered by your setup flow
- provider webhook subscription IDs used by webhook functions

Keep metadata small and use it for settings like these. Keep credentials out of metadata and use [connection configuration](#connection-configuration) for values the provider requires.

After creating the connection, use `updateMetadata` or [`PATCH /connections/metadata`](/reference/backend/http-api/connections/update-metadata) to change only the top-level fields you send. Each supplied field replaces its previous value, including when that value is an object. To replace the entire metadata object, use `setMetadata` or [`POST /connections/metadata`](/reference/backend/http-api/connections/set-metadata).

<Tabs>
  <Tab title="Node">
    ```ts
    await nango.updateMetadata('<INTEGRATION-ID>', '<CONNECTION-ID>', {
      syncArchived: false
    });
    ```
  </Tab>
  <Tab title="cURL">
    ```bash
    curl --request PATCH \
      --url https://api.nango.dev/connections/metadata \
      --header 'Authorization: Bearer <NANGO-API-KEY>' \
      --header 'Content-Type: application/json' \
      --data '{
        "connection_id": "<CONNECTION-ID>",
        "provider_config_key": "<INTEGRATION-ID>",
        "metadata": { "syncArchived": false }
      }'
    ```
  </Tab>
</Tabs>

Functions can read metadata for the connection they run for:

```ts
const metadata = await nango.getMetadata();
```

For deeper function patterns, see [Storage](/guides/platform/functions/storage).
